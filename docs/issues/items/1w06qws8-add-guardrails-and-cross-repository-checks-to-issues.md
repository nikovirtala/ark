# Add guardrails and cross-repository checks to issues

## Problem
issues 0.1.0 has the issue kind and its CLI, and nothing around them: no git hooks, no generated `index.md`, no checks over code, and references into other repositories are stored but never checked, in adr as in issues. A bad event is found only when someone runs `verify` after the commit exists. This is the second of the three pull requests that build issues in roadmap step 4 of `docs/00-ark-v1.md`: phase 2, guardrails, in `docs/02-issues-v1.md` "Implementation notes, roadmap and open questions".

## Proposal
- **Hooks**, through ledger's shared shims (ADR-0011): `pre-commit` (`verify --staged` and the index), `commit-msg` adding `Issue:` and `Issue-Event:` trailers for staged events and `Issue:` for the current issue set by `issues work`, with the warning when a message says "fixes" or "closes" an issue that has no staged `closed` event, `pre-push` and `post-merge`, as in `docs/02-issues-v1.md` "Git hook helpers".
- **`index.md`**: `issues index` and `[log] index = "committed"`, kept fresh on every write (ADR-0010).
- **CI checks**: every check in the "CI checks" table of `docs/02-issues-v1.md` runs in `issues verify`, including the checks over code that 0.1.0 doesn't run (scope globs, code anchors, stale anchors) and index freshness, next to the actor policy, implements, labels, orphans and closed-with-open-work checks.
- **References into other repositories and listing across sources, for adr and issues alike** (ADR-0005). Plain `verify` and `pre-commit` read only the cached source and never use the network; a source with no cache gives one warning ("<name> not fetched; references not checked"). `verify --fetch-sources` fetches each source's ref first, and CI and pre-push run with it; a failed fetch under it is an error, with the exit code chosen and justified by the design under ADR-0004. `<tool> sources fetch` refreshes the cache by hand. A qualified reference to a missing subject is an error; `implements` to a decision that isn't accepted is a warning. `ref` may be a branch, tag or commit; the docs recommend a tag or commit for reproducible CI, and `verify --json` records the resolved commit per source. Credentials are plain git's; the docs say how to give CI read access to private sources. `list` follows the same cache rule.
- **`verify --staged` widens its scope** (binding, from issues PR 1). When the staged diff touches an input that the checks read outside the issue log, `verify --staged`, and so the `pre-commit` hook, re-checks the issues that input affects: the local decision log (or any source the kind reads), `issues.toml`, and templates if template lint depends on them. Two cases are missed today: a staged `adr reject` or supersede alone doesn't re-check `issue/implements-unaccepted` on the issues that implement it, and a staged `issues.toml` policy change alone (`mcp_can_close`, `close_requires_human`, `[labels] exclusive`) doesn't re-check unchanged issues. The design picks the mechanism (a ledger `verifyLog` option or widening inside issues), checks adr for the same class (a staged `adr.toml` or template change under `adr verify --staged`), and fixes adr the same way.

## Alternatives
Cross-repository references could be fetched on every `verify`; that was rejected for decision 2 (fetch only when asked), so hooks stay offline and fast.

## Done when
- Released issues, adr and ledger versions ship the hooks, `issues index`, the checks and the cross-repository references described above, with tests, and the issues README no longer lists them as missing from the release.
- Under `issues verify --staged`, a staged `adr reject` alone reports `issue/implements-unaccepted` on an unchanged issue that implements the rejected decision, and a staged change to `mcp_can_close`, `close_requires_human` or `[labels] exclusive` alone reports the unchanged issues it breaks. Under `adr verify --staged`, a staged `adr.toml` or template change alone re-checks the decisions it affects. Tests cover each case.
- `verify` without `--fetch-sources` never uses the network, a source that isn't cached gives one warning, and a failed fetch under `--fetch-sources` exits with the code the design chose.
- ark's `docs/issues/issues.toml` sets `index = "committed"` with a committed `docs/issues/index.md`, and ark's hooks and CI run the new checks.
- The PR that does this work closes this issue in the same change, with a reason saying how each of these conditions was met.
