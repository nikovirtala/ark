# Review: ark Factory v1 Design

> **A record, not guidance.** This is a dated review of [`docs/05-factory-v1.md`](../05-factory-v1.md) at commit `dc76b2e`, kept as the cause of the revision that followed it. Its findings were settled in that revision; read the design doc for what holds now, and don't act on this page. When it was recorded, its links were pinned to the reviewed commit, and the sentence on links in Background was changed to say so; the rest is as written.

*Reviewed by Claude, 27 November 2026*

## Background

This review is based on the ark factory design doc, [`docs/05-factory-v1.md`](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md), as of 27 November 2026 (commit [dc76b2e](https://github.com/nikovirtala/ark/commit/dc76b2efe058679b7d6e38545547bd6dc0f79e0c)). It assesses the doc's pattern and design against three references:

- Notion's field guide [*A New Shape for Work*](https://www.notion.com/a-new-shape-for-work), which defines factories as shared AI systems on top of a shared context system and lays out a Notice → Plan → Run → Improve method.
- Kiro's blog post [*Building a software factory around human attention*](https://kiro.dev/blog/software-factory-human-attention/) (25 November 2026), which treats human attention as the limit on automation and describes a Discover → Triage → Design → Implement → Release → Monitor loop with a Learn step.
- The open-source [Kiro Factory Manual](https://github.com/kirodotdev-labs/sample-kiro-factory-manual) (README), the reference implementation behind that post.

The review was written from these documents alone, with no prior knowledge of ark, draft, kiro-remote or the deployment package beyond what the design doc says about them. Links to design doc sections point at the reviewed commit, so they show the doc as it was reviewed.

## Verdict

As a pattern, ark's factory is sound and in several places more rigorous than either reference: trust boundaries, release safety, state modelling, drift and now causality. It is weaker on the things both references treat as central: a learning loop, the ergonomics of human attention, and Notion's simplicity-first discipline. It also has two concrete holes in its own trust model.

## Where it lines up, and goes further

Against Notion's definition, ark qualifies cleanly. Notion defines a factory by three traits: specific, shared and scrutinized. ark is specific (papercuts plus the ready backlog), shared (its customers are agents across repositories, see [Problem](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#problem)) and scrutinized (shadow review and folded measures, see [Pilot and decisions](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#pilot-and-decisions)). Notion's simplest factory is a database with a status column and an agent that moves cards. ark's "every link is a kind with states, a closer and a timeout" ([The factory's state is data](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#the-factorys-state-is-data)) is the rigorous version of that idea. The rule in the same section that a reader folds history rather than trusting the latest status is a lesson neither reference states, and "no state that only one reader can see" (9t6n5jc6) is a sharper rule than either reference has for where factory state may live.

[One graph of the line](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#one-graph-of-the-line) is ark's answer to Notion's central thesis, that a factory sits on a shared context system, and it answers it without building a new store. The graph lives in draft, the tool that already reads every source of the line for the person, as an edges table with each measure as a named query. Unattended parts (the dispatcher, the breaker, the promote gate) never read this projection; they read their own sources. Causes are recorded where things happen rather than inferred later (ADR [6wh6egkw](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/adr/decisions/6wh6egkw-record-each-ledger-events-causes-in-its-envelope.md)), and the share of unknown causes is itself a measure. This is also what makes Kiro's question "does the factory need a person for the right reason?" answerable: a reason is a cause, and causes are now data.

The drift pass ([Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review), "Drift, deterministic first") is ark's version of Notion's "curing context rot": stale, misplaced and out-of-date context as the main enemy, with agents now making upkeep possible. ark goes further by selecting candidates deterministically, through standing with scope globs, before any model judges them.

On Kiro's open problem, ark already has a direction. Kiro admits its factory doesn't solve context and memory, that most of what a good reviewer knows still lives in people's heads, and that a new factory starts cold on a large repo. ADRs, standing, `implements` links ([Two intakes, one line](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#two-intakes-one-line), "Inside the frame by link") and the planned lessons ([Context](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#context)) are ark's answer to that. This is the strongest argument for building the factory on ark rather than on a generic board.

Security is the deepest part of the doc. The Kiro Manual says plainly that prompt instructions make a steered run less likely, not impossible, and that the real control is access. ark operationalises that idea in [Triage and the trust boundary](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#triage-and-the-trust-boundary) and [Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review): only a reproduction crosses into work, trust attaches at acceptance (teyqf2j9), the sandbox holds no credentials, `tools` lists enforce least privilege, and deterministic checks run before the reviewer.

Release is also far ahead of Kiro's Release and Monitor steps. The `next`/`latest` split and replay ([Release channels and promotion](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#release-channels-and-promotion)), the fail-closed breaker ([Circuit breaker and rollback](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#circuit-breaker-and-rollback)), and upgrade-downgrade testing with read-first-write-later ([Event format compatibility](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#event-format-compatibility)) have no equivalent in the Manual.

## The big divergence: autonomy

ark auto-merges routine work to `main` and auto-promotes it to every agent ([Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review), [Release channels and promotion](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#release-channels-and-promotion)). Kiro deliberately doesn't: it keeps human review on `main` for everything and gives the factory room to fail only in an internal edge build, using that build to gather evidence about which kinds of change could go without a reviewer. Notion also explicitly distances its factories from "dark factories" with no human oversight.

ark's compensating controls are real, but this is the bet everything else rests on. Kiro suggests two things ark lacks:

1. **An edge ring.** Today only a canary uses `next` ([Release channels and promotion](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#release-channels-and-promotion), "Bake"), so nothing sits between a scripted canary and every agent everywhere. A real-use ring would close that gap, for example one dogfood repo or a share of kiro-remote sessions on `next`.
2. **Graduated autonomy per kind of change.** The Manual records five risk levels without acting on them yet, to build a history to audit before any rule depends on them. ark's binary routine/frame split ([Problem](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#problem), "The frame") would benefit from recording the same history before step 4 of the [pilot](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#pilot-and-decisions) opens up whole lanes. With causes in place, that history becomes a walk: from each revert or breaker trip back to the kind of change that caused it.

## Holes in ark's own trust model

The first two findings below concern what the design doc calls **S2**, its "Untrusted reports" seam ([Seams and risks](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#seams-and-risks)). S2 is the route by which text injected into a report could steer a fix session or the reviewer, directly or through an issue an agent wrote, and from there reach every agent through auto-merge and `latest`. The doc rates S2 as one of its two highest-risk seams.

**Known-issue lines and warnings bypass the acceptance rule.** The doc says agent-written text is untrusted until a person accepts it ([Triage and the trust boundary](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#triage-and-the-trust-boundary), "Trust attaches at acceptance"). Yet triage, an agent working from untrusted reports, publishes "known issue ?42, workaround: …" lines. Every MCP server injects those lines into tool responses ([Detection and intake](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#detection-and-intake), "Known issues travel back"), and kiro-remote pushes the same warning into running sessions as a prompt ([Triage and the trust boundary](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#triage-and-the-trust-boundary), step 5 "Warn").

The `workaround` field is exactly where an attacker would put a payload. Reproduction proves the bug exists, not that the workaround text is benign. This is an S2 path that skips the reproduction gate and reaches every agent faster than any fix. Make these lines templated (issue id, tool, affected argument shape, "fix pending"), or require acceptance before free-text workarounds are published.

**Server instructions and tool descriptions aren't frame paths.** They are prompts shipped to every consuming agent: the doc itself puts the `report` rule in the server's instructions so it ships with the version ([Detection and intake](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#detection-and-intake), "The report tool"). Friction fixes, a routine lane, change exactly these strings ([Detection and intake](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#detection-and-intake), "Friction counts too"). Friction evals ([Release channels and promotion](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#release-channels-and-promotion), step 3) measure error rates, not intent. Yet the frame paths in [Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review) ("Frame routing, deterministic first") don't list them. Either add these strings to `CODEOWNERS` or add a required check that sends any diff to them to Niko until shadow review shows they're safe.

**Walks must respect the same boundary.** A walk from an issue back along causes reaches the report that started it ([One graph of the line](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#one-graph-of-the-line)). Today only people and measures walk the graph, which is fine. If a future step (a Learn step, a smarter drift pass) follows causes and pulls the text it finds into a prompt, that reopens the S2 chain. The graph should carry addresses, and any agent step that reads through it should follow the same "only the reproduction crosses" rule.

**Causes are claims, not facts.** Under ADR [6wh6egkw](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/adr/decisions/6wh6egkw-record-each-ledger-events-causes-in-its-envelope.md), the writing tool records causes from what it was given (a trailer, a flag, a hook's event), and `verify` checks only that an address is well-formed and, for a ledger address, that it exists. An agent can still name a wrong cause. Unattended readers don't use the graph and tripwires reopen decisions through Niko, so this is low-risk, but measures built on agent-supplied causes are only as good as those agents, and the ADR should say so.

**Two records of release state.** The doc's rule is "no state that only one reader can see" ([The factory's state is data](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#the-factorys-state-is-data)). The npm dist-tag meets that rule, since anyone can read it, but so does the ledger's Release kind, and both record the same fact: which version is on `latest`. That is the same split-truth risk as the GitHub deployment drill the same section cites. The doc says unattended readers read their own source; it should also say which source the promote job and the breaker read for "what's live" (the tag) and which for history (the ledger), and add a reconciliation check. The "frame label", used throughout [Overview](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#overview) and [Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review), also sits awkwardly with "nothing in GitHub labels"; say it's a projection of a ledger fact.

## Attention: Kiro's core lesson, only partly absorbed

Kiro found its factory stopping to ask too often. It now settles choices an ordinary change could undo, states the choice and the alternative on the PR, and escalates only when a choice is hard to undo, such as persisted data, public interfaces or security behaviour. ark's frame definition ([Problem](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#problem), "The frame") captures irreversibility, and its new measures make attention visible: "wakes done by hand" and "open ends" are both walks in [One graph of the line](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#one-graph-of-the-line). Its escalation paths, though, are scattered across eight sections, and several send plumbing to Niko as if it were a decision:

- **Failed required checks.** Any failure goes to Niko ([Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review), "Required checks"), even author-fixable ones like Evidence naming a test that didn't run, a stale screenshot or the commit format. These should loop back to the author like review findings. Only the invariant checks should escalate: repro tampering, test deletion, factory code, canaries.
- **Liveness failures.** A reviewer with no verdict after 2 hours, or a bake that can't finish in 72 hours ([The factory's state is data](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#the-factorys-state-is-data), kinds table), are factory-health problems, not frame decisions. "Open ends" now counts them; route them to an ops signal, like the Manual's janitor worker and report page, rather than into Niko's decision lane.
- **Thin escalations.** An escalation currently arrives with "the reviewer's verdict as its evidence" ([Overview](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#overview)). Kiro's PRs carry a page describing what changed and why, the alternatives weighed, what each check found and what wasn't run. Each acceptance request should name the one decision, the options, whether it's reversible, and the default the factory would take.

Two more additions would help. A single table listing every path to Niko, in the spirit of the Manual's per-prompt `### Escalate` contract. And one more walk in [One graph of the line](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#one-graph-of-the-line): escalations Niko settled with the factory's default. Those are candidates to stop escalating, and counting them is how Kiro's "for the right reason" becomes a number.

## The missing step: Learn

The doc mentions lessons as planned ([Context](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#context)) but has no learning loop. Kiro's Learn step reads every correction on board items and PRs and proposes skill changes, which a person reviews before applying. Notion's Improve step versions prompts and tests them against evals before switching everyone over.

ark has fragments of this: the ladder from repeated drift findings to checks and person's-checks that become required checks ([Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review)), review findings per pass ([Pilot and decisions](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#pilot-and-decisions), measures), and now the walk from a contradicted assumption back to the decisions that rest on it ([One graph of the line](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#one-graph-of-the-line)). But nothing turns Niko's reverts, frame-lane edits or disagreements with the reviewer into changes to the rubric, recipes or server instructions.

The causes make this cheap to add. Define Learn as a kind in [The factory's state is data](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#the-factorys-state-is-data) whose input is a walk, from a correction back along causes to the review, recipe and standing that let it through, and whose output is a frame-labelled PR. Build a reviewer eval set from shadow-review history (each PR with Niko's settlement) so a rubric or model change is regression-tested the way the reproduction corpus tests the product.

## Simplicity

Notion warns against adding complexity early, a mistake it says LLMs make even more eagerly than people, and recommends running a simple factory, watching it fail, and fixing the failures you actually see. This doc, drafted by Claude, carries 7 kinds ([The factory's state is data](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#the-factorys-state-is-data)), 5 promotion gates ([Release channels and promotion](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#release-channels-and-promotion)), 10 required checks and 3 review passes across two vendors ([Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review)), canary strings ([Triage and the trust boundary](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#triage-and-the-trust-boundary)), hash-matched recipes, friction evals and 13 tripwired decisions ([Pilot and decisions](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#pilot-and-decisions)). It also depends on draft (acceptance, the map and now the graph), kiro-remote, the deployment package and two still-proposed ADRs: va08e4c3 and 0j5y197e.

The graph section shows the right instinct: a new need answered by a projection in an existing tool, not a new system. The staged pilot and the "starting value plus tripwire" framing ([Pilot and decisions](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#pilot-and-decisions)) mitigate the rest well. What's missing is a mapping of each defence to the pilot step that switches it on, with anything not tied to an observed failure deferred. Canary strings, friction evals, the reviewer-drift breaker trigger ([Circuit breaker and rollback](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#circuit-breaker-and-rollback)) and the local-session hook ([Detection and intake](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#detection-and-intake)) look like candidates to defer.

Small sample sizes matter here too. With about 11 sessions an evening ([Circuit breaker and rollback](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#circuit-breaker-and-rollback)), "shadow review rarely disagrees with Niko" needs a minimum count of reviewed PRs before it can gate step 4.

Finally, by the doc's own drift thesis, it is a rot risk. Agents will read it as instructions, and it mixes stable design with dated anecdotes and decision history, such as the 18 November backlog table in [Two intakes, one line](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#two-intakes-one-line). Measures are now also described twice, in the walks table in [One graph of the line](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#one-graph-of-the-line) and the measures table in [Pilot and decisions](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#pilot-and-decisions), which can drift apart. The doc already shows this: its open decisions in [Pilot and decisions](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#pilot-and-decisions) still list 6wh6egkw as proposed, though it has been accepted. Splitting the doc into design, decisions (in the ledger) and a pilot log, with one measures table, would practise what it preaches.

## Top three recommendations

1. **Template the known-issue and warning text** ([Detection and intake](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#detection-and-intake), [Triage and the trust boundary](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#triage-and-the-trust-boundary)), or require acceptance before free-text workarounds reach other agents.
2. **Frame-gate instruction and description strings** in the MCP servers, by adding them to the frame paths in [Fix and review](https://github.com/nikovirtala/ark/blob/dc76b2efe058679b7d6e38545547bd6dc0f79e0c/docs/05-factory-v1.md#fix-and-review).
3. **Add a Learn kind built on causes, with a reviewer eval set**, so Niko's corrections improve the factory instead of only fixing individual PRs.

The first two close real S2 holes; the third is what both references treat as the reason to have a factory at all, and the graph of causes has already done most of the work for it.
